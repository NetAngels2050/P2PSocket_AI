## 2. 方法

### 2.1 总口径（TD-24 环境分级）

- **L1 本地自动化**：in-proc 全链本机回环——内存 SQLite 服务端（控制面+中继数据面+审计）+ 双客户端运行时 + NatSimulator（与集成测试 link 编译同一源文件=单一事实源）+ TCP echo 载荷终点。**每格/每样本独立世界**（独立库/服务端/客户端/NAT，销毁即隔离）。
- 回环别名拓扑：模拟公网 127.0.0.1 / 客户端 A=127.0.0.4 / 客户端 B=127.0.0.5 / STUN 派生 :3478。
- **标注：L1 吞吐/延迟为本机基线测量 ≠ 真实网络性能**；打洞矩阵为 NAT 模拟语义的确定性结果（与真实 NAT 行为的一致性归协议设计文档 02 §5）。
- **L2 实机**：公网服务器 punch_stats 表脱敏聚合（服务器端 python3 sqlite3 只读查询，聚合结果落 l2-punch-stats.txt）。

### 2.3 关键机制口径（读数前提）

- **TCP 打洞端口预测（02 §5.2）**：N 条并发 connect 瞄准"对端 STUN 映射端口+(N−1)"——N=1 即瞄当前已知映射端口，双向 SYN 交叉同时打开（simultaneous open），**不依赖 NAT 分配规律（Random 分配也通）**；N≥2 需两侧顺序分配，任一 Random 侧必 miss→回退中继。
- **UDP 打洞（02 §5.1）**：THello 连发（无端口预测）——cone×cone 可直连；涉及 symmetric 全 miss→回退。
- **回退资格**：打洞 Ack 后失败才有回退资格；UDP 全阻塞在 Ack 前即失败→failed（无回退）。
- **relay 建立耗时含 10s 打洞超时窗**：回退语义=打洞尝试预算（10s）用尽后才回退（05 §6）——relay 段耗时 ≈ 超时窗+回退建立。

## 4. 结论与瓶颈分析

### 4.1 NFR-11 五要素结论

| 要素 | 结论 | 出处 |
|---|---|---|
| 单隧道吞吐（TCP 映射） | 直连 4 流 217.7 Mbps / 中继 4 流 198.6 Mbps（L1 回环基线；中继档≈直连档的 91%） | §3.3 |
| 新增延迟（直连/中继分别测量） | 直连隧道 vs 裸回环 +0.223 ms（p50）；中继再 +0.039 ms——封装+加密+分帧每往返约 +0.22ms（回环口径），真实网络 RTT 为几十 ms 量级时占比可忽略 | §3.4/§4.3 |
| 并发映射数 | 8 映射并发无死锁、吞吐 219.2 Mbps 与单隧道 4 流档相当（并发线性扩展无退化） | §3.5 |
| 服务端并发设备数 | 500（=配置上限）全 established，稳态 CPU 0.7%（2C 机器进程内口径）、工作集 ~236MB | §3.7 |
| 打洞成功率（按 NAT 类型） | UDP cone×cone 9/9 直连、涉 symmetric 16/16 回退；TCP N=1 任意组合直连、SS×SS 全 N 直连、涉 Random N≥2 回退；L2 实机 relay 99.07%（拓扑必然，见注记） | §3.1/§3.8 |

### 4.2 吞吐瓶颈定性

裸回环 4376 Mbps → 直连隧道 175~218 Mbps（≈4~5%）：**瓶颈不在网络传输（L1 无真实网络），在端侧全栈处理**——PTP 分帧（1368B 明文块切分）、AES-GCM 加密封装、WINDOW 信用往返（64KiB 窗口）、TCP 承载复制。三个隧道档（identity/predict/relay）4 流档 198.6~218.4 Mbps 相互接近（±5% 内）说明：**直连与中继的路径差异不构成主要瓶颈**——中继转发为 8B 头剥离的零解密转发（02 §6.2），服务端转发开销小；瓶颈统一在两端加解密+分帧。**推论：真实网络部署中，隧道吞吐将受两端 CPU 与物理带宽双重约束，中继路径不额外劣化。**

小包档（1KB）：直连 165.5 / 中继 72.2 Mbps——小包高频往返下单流吞吐下降明显（帧开销占比上升+信用回报频密），多流并发可摊平（4 流档回升至 ~200）。

### 4.3 延迟开销换算

loopback-echo p50 0.072ms → tunnel-echo 0.295ms（**+0.223ms/往返**）→ relay-echo 0.334ms（**再 +0.039ms**）。
即：PTP 封装+AES-GCM 加密+分帧+信用处理的往返开销约 0.22ms（回环放大口径：本地处理时间，与传输距离无关）；中继经服务端转发仅增加约 0.04ms（本机回环内服务端同机，真实网络中中继增加一跳物理 RTT）。**该绝对开销相对真实网络 RTT（公网 tens of ms）可忽略；用户感知延迟主要由物理网络决定。**

### 4.4 打洞成功率机制结论

1. **TCP N=1 是全组合直连的保底路径**：offset+0=瞄准对端 STUN 当前映射端口，双向 SYN 同时打开——不依赖 NAT 分配规律（Random 亦通）。SR×SR 这类最不利组合 N=1 也 direct。
2. **N≥2 端口预测需双侧顺序分配**：SS×SS 全 N 直连；任一 Random 侧 N≥2 必 miss 回退（随机分配无法预测）。
3. **UDP 对称组合不可穿透**（THello 无端口预测语义）：涉 symmetric 全回退——符合 02 §5.1 设计预期；L2 家宽 CGNAT 实测印证。
4. **UDP 全阻塞无回退资格**：Ack 前失败→failed（用户侧解法=开设备级中继回退开关，失败即转 relay 承载）。
5. **failed 率整体 0.37%（L2）且全部可归因**（缺陷窗口 4 例已修复+回退未开 3 例+调试期 2 例）——当前版本无不可解释失败。

### 4.5 NFR-14"秒级"判定

- **直连场景满足**：p50 219ms / p95 234ms（L1），L2 实机 direct p50 192ms——亚秒级。
- **回退场景 ~10.2s**：relay 建立 p50 10187ms（L1）/9957ms（L2）≈10s 打洞超时窗+回退建立（设计语义：预算用尽才回退，保证能直连则直连）。**用户可感知层面的"秒级"在回退路径表现为约 10s**——这是打洞尝试预算的固有成本（可经配置收窄超时窗换取更快回退，代价是慢速可穿透组合的直连机会）。此为设计权衡，如实呈报。

### 4.6 资源结论（NFR-13）

服务端 500 设备稳态 CPU<1%、工作集 ~236MB（in-proc 含设备模拟开销；真实部署拆进程后客户端侧各进程另计）——2C/2GB 规格 VPS 承载 500 设备+中继转发余量充足（当前实测生产负载远低于此）。客户端进程句柄 2357/线程 57 为全栈满载峰值，正常水位（稳态窗）CPU 0.4~0.7%。

## 6. 范围与局限

1. **L1 回环吞吐/延迟 ≠ 真实网络性能**（TD-24）：无物理带宽约束、无丢包/抖动；其价值在同机相对对照（直连 vs 中继 vs 裸基线、版本间回归基线）。
2. **两台 VPS iperf3 实机吞吐=预留位**（环境依赖）：补测方法=同机房两台 VPS，iperf3 -c 虚拟IP:映射端口（经隧道）vs iperf3 直连基线，场景矩阵 {直连 UDP/TCP、中继 UDP/TCP}×{1 流、4 流}+CPU/内存采集（设计 09 §3.1 原始方案）。
3. **24h 稳定性**（09 §3.3：持续传输+周期 REKEY+中继↔直连切换）未纳入本报告——由 CI 全量测试（每任务交付轮持续满载全绿）+L2 生产 10 天自然运行（当前版本零 relay_failed）替代佐证；专项 24h 基准随测试自动化另行覆盖。
4. **⑦设备规模 in-proc 口径**：服务端与设备模拟同进程，CPU/内存含双方；真实部署为独立进程，网络栈与进程隔离开销另计。
5. **L2 punch_stats 为生产自然流量**（非受控基准）：组合分布由该部署拓扑决定（见 §3.8 注记）。
6. rtt 段口径说明：Stopwatch 微秒精度升级（原毫秒采样在回环亚毫秒大量取整为 0）后以终版 harness 单独重测两轮呈报；其余六段沿用全量两轮（§2.4）。
