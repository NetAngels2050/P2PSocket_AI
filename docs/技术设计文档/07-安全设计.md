## 1. 密钥体系总览

| 密钥 | 生成 | 存储 | 用途 | 生命周期 |
|---|---|---|---|---|
| 设备静态密钥对（P-256） | 客户端首次注册时生成 | 私钥：客户端本地（DPAPI/0600）；公钥：服务端 devices 表 | 隧道握手身份绑定（static-static ECDH） | 设备身份存续期 |
| 登录临时密钥对（P-256，v1.67） | 服务端每连接 Hello 时生成（§10） | 服务端内存（连接生命周期内） | 0x20/0x21/0x23 密码字段 ECIES 封装的接收钥 | 单连接（关闭即弃） |
| deviceSecret（32B） | 服务端注册时 CSPRNG 生成，**ECIES 加密下发**（OQ-15，见 §5） | 双端（服务端库内[§14.3 静态加密] / 客户端本地加密） | 控制通道 HMAC、STUN 认证 | 重置/解绑/凭据恢复时轮换 |
| connMacKey | 每次控制连接握手 HKDF 派生 | 内存 | 控制消息 seq HMAC | 单连接 |
| 会话密钥（发送/接收各 32B） | 每次隧道握手 HKDF 派生 | 内存 | PTP 帧 AES-256-GCM | TTL 3600s（REKEY 轮换，SEC-14） |
| 数据静态加密主密钥（32B，v1.67） | 管理员配置（appsettings/环境变量，§14.3） | 服务端配置（**不落库**，SEC-83） | deviceSecret 落库加密 | 人工轮换（双钥窗口） |
| 用户口令哈希 | 注册时 PBKDF2-SHA256（100k 迭代、16B 盐） | 服务端 users 表 | Web 登录 | 改密时重建 |

派生函数统一：`HKDF-SHA256(ikm, salt, info, len)`；随机源统一 `RandomNumberGenerator`（CSPRNG）。

## 2. 数据面加密（SEC-11/12，02 §4）

- AEAD：`System.Security.Cryptography.AesGcm`（AES-256-GCM，硬件加速），tag 16B；
- nonce：64bit counter 小端填充 12B，**每方向严格单调**；接收端维护滑动窗口（64）拒绝重复/回退（防重放）；
- AAD 绑定帧头（ver/type/channelId/len），防帧裁剪与类型篡改；
- 机密性/完整性/防重放三项能力由此满足；中继路径下密钥不变 → **服务端不可解密**（SEC-11 的中继不可解密要求）。

## 3. 握手与身份防冒充（SEC-21，02 §4.1）

- 双重 ECDH：`ECDH(ephA,ephB)`（会话独立性）⊕ `ECDH(staticA,staticB)`（身份绑定）→ HKDF 派生会话密钥；
- 静态公钥经服务端 PunchInvite 下发 → 信任来源是服务端（SEC-13"控制面协助交换"）；
- 握手消息带 HMAC（以 static-static 共享密钥为 IKM 派生的握手密钥）验证，防中间人篡改握手报文；
- 冒充者无目标设备私钥 → 无法通过 TConfirm 验证 → 会话建立失败。

## 4. 控制通道安全（SEC-22，02 §2）

- 连接级：Hello 挑战（nonceC/nonceS）→ Proof(HMAC(deviceSecret)) → 派生 connMacKey；
- 消息级：每条消息 `seq 单调递增 + ts ±120s 窗口 + HMAC-SHA256`；校验失败立即断连并记审计；
- 重放防御三层：seq（连接内）、ts（跨连接窗口）、nonce 去重（STUN 侧缓存 5min）；
- **时钟对齐（OQ-12）**：Hello 阶段不校 ts（尚无共享时间基准）；HelloAck 携带 serverTs，客户端按 RTT/2 补偿计算 offset 后再发 Proof；超窗回 5005 TIME_SKEW 供重校准重试——消除"时钟偏差死锁"（原设计 Proof 先于校准被拒，形成无法进入协议的环）；0x30 Ack 周期性重校 offset 跟踪漂移。
- **本机地址披露（v1.63，NET-76 候选交换的注记）**：0x70/0x76 的 localCandidates 将本机网卡 IPv4（乘打洞监听口）披露给对端（并经服务端存转）。威胁评估：①接收方须先过 L2 授权（同账号 ∪ 共同分组，SignalingCoordinator 打洞校验前置）——候选只发给已可建隧道的对端，不进入任何列表接口；②候选端口为打洞会话临时随机口，握手本身承载 PTP 身份挑战（SEC-21 staticPubKey+ECDH），直连到达者若无会话密钥无法完成握手；③服务端纯存转不解析落库；④控制通道明文可见性与 R1 既有口径一致（端点信息类，已知情接受）。100.64.0.0/10 虚拟网段已从候选中滤除（非物理可达地址）。

## 5. 注册与滥用防护（SEC-61/62，PRD 威胁 T3/T10/R2）

### 5.0 现状勘误（v1.67，M5-01 漂移实录）

本节 v1.5~v1.66 版本曾声称：「防护 = ②单 IP 注册频率限制（如 10 次/小时，内存令牌桶）③设备总数上限（server_config `max_devices`）」。**安全评估（2026-10-21）查实：②③均未实施**——注册路径（RegistrationService）不读取 `max_devices` 键、无任何频控；且新设备入默认分组**硬编码 `Approved=true` 直入**（默认分组 JoinPolicy 仅约束 0x51 凭码入组，不约束注册路径）。**教训**：设计文档以「列表式承诺」描述防护而无任务承载，实现侧静默缺位——M5-02/03 立项补齐。本节 §5.1/§5.2 为 **M5 目标设计**（编码前定案），漂移台账另见 10 §10 与本册 §15.1。

### 5.1 注册准入三重闸门（SEC-61，M5-02）

| 闸 | 机制 | 配置（03 §2.8） | 缺省 |
|---|---|---|---|
| ① 开关 | `device_registration_open`：关 → 拒；管理页系统配置白名单键、写库即生效（注册路径现读，relay_enabled 同模式） | `device_registration_open` | **1（开放，OQ-20③ 兼容现状）** |
| ② 单 IP 频控 | 内存令牌桶（StunGuard `TakeNoLock` 同款：TimeProvider 计时、容量=速率、初始满桶；键空间上限 8192+60s 空闲清扫）；键=控制连接源 IP | `register_rate_per_ip` | 10（次/小时/IP，容量 10） |
| ③ 总量上限 | 注册**新建**设备前 `COUNT(devices) ≥ max_devices` → 拒 | `max_devices`（既有键） | 500 |

- **闸三对覆盖式恢复的口径（定案）**：查表动作覆盖注册与覆盖式恢复两路径；**拦截仅作用于新增行的路径**——覆盖恢复命中既有行（OQ-14）不新增设备数，放行（否则达上限后存量设备凭据丢失即被永久锁死）；原设备行已被删（解绑）的恢复请求视同新注册受闸三约束。
- **拒绝错误码（M5-01 定案，04 §5 新增）**：三闸门统一 `Error 4006 REGISTRATION_DENIED`、httpLikeMsg 固定 `registration_denied`——**对外不区分闸门**（区分响应=免费探测 oracle：陌生注册者可枚举开关状态/频控边界/容量余量）；拒因维度仅入审计 `register_deny`（detail: `reason=switch|rate|quota`、ip）。拒绝后连接停留 NeedRegister（客户端可重试，不断连）。
- **2004 复用被否**：2004=REGISTRATION_CLOSED 语义绑定「用户注册开关关闭」（0x20 既有），覆盖频控/总量拒因将造成错误码语义漂移；04 §5 错误码表是协议契约，宁加不改（加法演进）。
- 既有防护不变更：⑤同 mac_code 在线重注册 → 4004（OQ-14）；⑥RegisterAck deviceSecret 以客户端 staticPubKey ECIES 加密下发（OQ-15）。
- 0x20 用户注册开关 `registration_open`（既有）与设备注册开关 `device_registration_open` 相互独立——前者管账号开立、后者管设备准入。
- **落地注记（v1.68，M5-02 已实施 2026-10-22）**：闸①②置于 macCode 查表**前**（新建与覆盖式恢复同拒——拒绝语义针对注册尝试本身）、闸③查表后仅拦 `existing==null` 新增路径（恢复分支天然放行）；闸②=独立 `RegistrationGuard`（StunGuard TakeNoLock 同款，速率单位=次/小时，键=控制连接 RemoteEndPoint.Address；构造可空注入，未装配或源 IP 不可得=进程内/测试装配跳过）；4006=`ErrorCode.RegistrationDenied`（Core 码表唯一来源）；`device_registration_open`/`register_rate_per_ip` 入 ConfigDefaults 幂等种子（存量部署升级启动即补键），前者注册路径现读即时生效、后者启动期读入令牌桶（管理页 restartRequired 标注）；管理页系统配置表按后端 items 泛型渲染，KEY_META 补标签与控件类型即上页。

### 5.2 注册入组遵循默认分组策略（SEC-62，M5-03）

- RegistrationService 入组分支改读默认分组 `JoinPolicy`：
  - `free` → group_members 写入 `Approved=true`（现状行为不变）；
  - `approval` → **join_requests 建 pending 行**（与 0x51 凭码入组同语义），不写 group_members——组内不可见（可见性=approved 成员行口径，05 §5 L2 同源）；审计 `group_join_request`（detail 注 `source=register`）。
- RegisterAck.groupInfo[] 仅含 approved 行 → approval 策略下注册成功但分组列表为空，向导如实呈现「待审批」。
- 审批承载复用既有件：0x53 审批队列（默认分组 owner=内置 admin）+ 服务端 Web `/api/group-requests?status=pending`（FR-S-305）；批准走既有入组链（group_join_approve 审计 + 0x41 推送同口径，M2-09/10 纪律）。
- **落地注记（v1.69，M5-03 已实施 2026-10-22）**：入组分支读行值 `JoinPolicy`（管理页 PUT 双写键+行即时生效，M3-05 件不动）；approval 建 pending 行**不带登录态**（0x51 重复申请去重天然覆盖：同组同设备已有 pending 不重复建行）；审计 `group_join_request` detail 注 `Source=register`（既有共享核口径：审批审计行 DeviceId=审批者，被批准设备在 detail）；RegisterAck 分组查询加 `Approved` 过滤；向导完成页空组渲染「待审批」标签（`wizard-pending-approval`）；free 行为不变（现状直入）。

### 5.3 其余注册防护（不变）

- MAC 识别码仅作注册输入，**权威身份是签发的 deviceId**（D6）：克隆机器拿不到原设备私钥与 deviceSecret，无法冒充在线设备；凭据丢失后的重注册走覆盖式恢复（OQ-14：离线方可覆盖，在线必须管理员解绑）；
- 服务端数据库文件权限：Linux `0600`（服务账户）/Windows ACL 仅服务账户与 Administrators。

## 6. 凭据本地存储（SEC-23）

| 平台 | 方案 |
|---|---|
| Windows | `ProtectedData`（DPAPI，机器范围）加密 deviceSecret 与静态私钥后写入 state.json |
| Linux | state.json `0600`、目录 `0700`（root 或专用服务账户） |

> 实现注记（P2 方案 a，2026-10-11 批复）：登录态保持（"记住我"）新增记住的账号密码——
> 密码与 deviceSecret 同 `ISecretProtector` 机制同级保护（Windows=DPAPI 机器范围+用途熵、
> Linux=明文+0600，上表口径不变）；用户名非机密（日志/UI 均展示）明文落盘。语义边界：
> 登录即记住、登出即忘记（清除凭据）、重启自动重放 0x21；重放失败（密码已变更）即清除凭据。
> 威胁模型影响：设备持有人（或能读 state.json 的本机恶意软件）额外获得账号密码——
> 与"设备持有=设备身份可用"相比扩大至账号级，属用户显式批复接受的权衡。
> **M5 注记（v1.67）**：重放的 0x21 走 §10 ECIES 封装（每次发送现加密，非密文重放）。

## 7. 授权执行点（SEC-52，PRD 05 §4 判定链）

| 层 | 执行位置 | 失败动作 |
|---|---|---|
| L1 能力模式 | 服务端 ControlSession 分发器 | Error 2002 + 审计 |
| L2 目标授权 | 服务端 Authorizer（SQL：账号设备 ∪ 共同分组） | Error 4001 + 审计 `punch_deny` |
| L3 地址白名单 | 服务端（下发 PunchInvite 前）+ 对端 MappingEngine 执行点双重校验 | Error 4002 + 审计 `mapping_deny` |
| 远程码 | 仅查找别名，不构成授权（D7） | Error 4003 |
| 授权失效事件 | 登出/退组/白名单移除/码重置/禁用 → 服务端推送失效（0x75 Invalidation，02 §2.4）→ 双端映射状态机 → invalid | 停止转发 + 双端提示 |

## 8. 管理面（PRD 07 §4 决策的落实）

- 客户端本地 API：仅 `127.0.0.1` 监听（D11）+ **请求 token 鉴权（v1.67/SEC-82，§14.2——"无鉴权"旧口径废止，TD-12 的"无鉴权"表述由 M5-12 修订为 token 鉴权+回环双层）**；
- 服务端 Web：仅本机监听；管理员 Cookie 会话（HttpOnly/SameSite=Strict）；远程管理仅经 F7 隧道；**IP 黑名单中间件前置（§13.3）**；
- 升级引导链路（FR-C-904）无认证依赖：UpdateInfo 为只读公开内容（版本号与指引+产物哈希展示，§14.4），不泄露业务数据。

## 9. 残余风险与技术对策对照（PRD 07 §9）

| PRD 风险 | 本设计的对策 | 残余 |
|---|---|---|
| R1 HTTP 明文 | 决策维持；控制通道有 HMAC 完整性（无机密性——信令含端点信息，属已知情接受范围；M5 后登录密码字段经 SEC-26 加密，明文面收敛为元信息） | 信令明文可见（非业务数据） |
| R2 MAC 重复/伪造 | deviceId + 私钥权威身份（§5）；在线设备拒绝覆盖式重注册（4004） | 无 |
| R3 TCP 预测命中率 | 并发路数 N 可配（1~5），A-5 实测调优 | 随机型 NAT 依赖中继 |
| R4 UDP 被封 | TCP 打洞 + TCP 中继承载（FR-S-704） | 无混淆（SEC-15 扩展位保留，PTP 帧外层可插拔） |
| R6 admin/admin | 首登提示改密；命令行重置工具（`--reset-admin`）；防爆破延迟阶梯（§11，admin Web 与 0x21 共享 IP 维计数） | 弱口令未强制修改（R6 口径不变） |
| R7 注册链路主动 MITM | RegisterAck 经 ECIES 加密 deviceSecret（OQ-15，防窃听）；攻击者若在注册期**替换**客户端 staticPubKey，可令服务端加密的 secret 对其可读并接管该新注册身份 | 一次性窗口攻击，需注册期持续 MITM；已知情接受；后续可选：服务端 Web 展示设备公钥指纹供管理员人工核对 |
| R8 登录族加密密钥分发 MITM（v1.67） | HelloAck.loginEphPub 未经认证（D21 无 TLS 前提）；SEC-26 目标=链路**嗅探**不可得明文（达成）；主动 MITM 替换公钥可截获密码（§10.4） | 与 R7 同族的主动窗口攻击，已知情接受；抗主动 MITM 的根治载体是 TLS/密钥 pinning（随 R1 长期选项一并评估，ephemeral 方案下 pinning 不可用——见 §10.1 决策对比） |

## 10. 登录族密码字段加密传输（SEC-26，v1.67/M5，TD-25）

> 依据：SEC-26（沿 OQ-15 模式）、OQ-20②（D21 维持不引 TLS，元数据明文留 R1）、OQ-21①（**混布升级窗口=硬切**：服务端不设明文过渡双轨、旧客户端明文登录一律失败；自家机队先客户端后服务端单一维护窗口；客户端对旧服务端行为由本节定案）。

### 10.1 封装格式与密钥选型（定案：每连接临时服务端密钥对）

- **服务端密钥**：每连接临时密钥对 `loginEph`（P-256）——ControlSession 在 Hello 处理时生成，公钥随 HelloAck 下发，私钥仅存会话内存，**连接关闭即弃**。
- **封装结构**（与 RegisterAck 既有 ECIES 同构，OQ-15 模式）：

```
box = [ephPub 65B][nonce 12B][AES-256-GCM 密文‖16B tag]
key = HKDF-SHA256(ECDH(ephC, loginEphS), salt=∅, info="pcp-login-v1", 32)
```

- 复用 `P2P.Core/Crypto/Ecies`：info 参数化（缺省 `"p2p-ecies"` 不变，既有 RegisterAck 调用零改动）；登录族独立 info 实现**域分离**（防跨用途密文混用）。
- **三种候选对比（新自由度推演）**：

| 候选 | 前向保密 | 密钥运维 | 结论 |
|---|---|---|---|
| 服务端**长持**密钥对 | ✗（私钥一旦泄露可回溯解密历史录流） | 生成/持久/备份一致性/泄露处置 runbook 全套 | 否决 |
| **每连接临时**密钥对（定案） | ✓（私钥用后即焚，录流+日后任意静态密钥泄露均不可回溯） | 零（无持久化、无备份项、无泄露处置） | **定案** |
| 对称 `HKDF(deviceSecret)` | ✗（库泄露+录流=回溯） | 零分发 | 否决：密码机密性耦合设备凭据（0x20 用户注册密码由设备钥保护语义错位）；deviceSecret 已承担 Proof/STUN 两用途，第三用途违反密钥分离原则 |

- ephemeral 定案的代价与接受理由：无法引入客户端公钥 pinning（每连接公钥都变）——M5 本就不做 pinning（自部署单服务器，pinning 增加换机/迁移摩擦且引入「指纹变更=疑似攻击」告警疲劳）；若未来需要抗主动 MITM，正确载体是 TLS（R1 长期选项）而非 pinning。
- **0x23 会话已建立语境（定案）**：不复用会话协商结果——connMacKey 是 HMAC 完整性钥（非机密性钥），从中派生加密钥使 deviceSecret 体系承担第二用途；且 0x20/未登录 0x21 无会话可复用。三消息统一走同一封装（一条实现路径）。
- **密钥分发时序推演（血缘完备）**：已注册路径 Hello→HelloAck(loginEphPub)→Proof→established→0x21；未注册路径 Hello→HelloAck(loginEphPub)→0x10→RegisterAck→established→0x20/0x21——**loginEphPub 到达恒先于任何携密消息**（02 §2.3/§2.4 字段随更）。

### 10.2 协议字段变更（02 §2.3/§2.4 随更，加法演进）

| 消息 | 新增可选字段（尾部） | 说明 |
|---|---|---|
| HelloAck | `loginEphPub: byte[65]?`（Key 8） | 本连接登录加密公钥；缺失=旧服务端（§10.3 客户侧行为） |
| 0x20 UserRegister | `passwordBox: byte[]?`（Key 5） | 密码 ECIES 密文；legacy `password` 字段保留定义但服务端硬拒 |
| 0x21 UserLogin | `passwordBox: byte[]?`（Key 5） | 同上 |
| 0x23 UserChangePassword | `oldPasswordBox: byte[]?`（Key 5）、`newPasswordBox: byte[]?`（Key 6） | 两个密码字段分别封装 |

- 尾部可选字段=既有混布兼容模式（punchConcurrency/localCandidates 先例，MessagePack 尾部容忍）；**protocolVersion 维持 v1**——字段层纯加法；行为层硬切是服务端安全策略而非格式破坏，02 §7 加法规则满足；**不启用「相邻旧版本兼容窗口」**（02 §7 该机制=版本递增后的双轨兼容，与 OQ-21① 硬切明令冲突，本变更不走版本递增路径故不触发）。

### 10.3 硬切口径（OQ-21① 定案落点）

**服务端**（M5-06）：

- 0x20/0x21/0x23：`passwordBox` 缺失 **或** legacy 明文字段非空 → `Error 5004 "password_ecies_required"`（VERSION_NOT_SUPPORTED 语义复用：旧客户端收到后在 UI/日志呈现「协议版本不兼容」引导升级，比「密码错误」误导性小；无明文过渡双轨）；
- `passwordBox` 解密失败（篡改/错钥）→ Ack `Ok=false`（凭据失败统一口径，**不泄漏具体原因**——A-16 单测断言点）；
- 0x10 Register 携带 `Password` 字段（双端未使用的死字段，§15.2 勘误）→ 同 5004 拒（封堵平行明文通路，保 P0 修复完备性）。

**客户端**（M5-06）：

- HelloAck 无 `loginEphPub` → 标记本连接登录加密不可用；0x20/0x21/0x23 发送前置检查 → **本地拒绝**（本地 API 映射 5004，文案「服务端版本过旧，不支持加密登录，请先升级服务端」），**不回退明文**——回退=主动 MITM 剥除 HelloAck 字段即可迫使「新客户端+新服务端」降级明文（downgrade attack），OQ-21① 硬切收益归零；
- 记住我自动重放遇旧服务端：跳过重放、**保留凭据**、下轮重连再试（M2-15「发送异常保留凭据」同语义；凭据被拒[密码已改]才清除）；
- 升级序（自家机队）：**先客户端、后服务端**单一维护窗口——窗口期新客户端对旧服务端仅登录族不可用，设备级功能（哑节点同步/映射被动面/打洞响应）不受影响。

**混布行为矩阵（A-16 断言依据）**：

| 组合 | 行为 |
|---|---|
| 旧客户端 + 新服务端 | 明文 0x21 → Error 5004，登录失败（硬切，OQ-21①） |
| 新客户端 + 旧服务端 | 本地拒绝 5004+升级提示，不发送明文 |
| 新客户端 + 新服务端 | ECIES 密文，帧 dump 无明文密码子串（A-16 探针断言） |
| 明文重放 | 任何组合下不发生（客户端无明文发送路径） |

### 10.4 残余风险 R8（登记于 §9）

HelloAck 本身未经认证（D21）——注册期/首连期**主动** MITM 替换 loginEphPub 可令密码对攻击者可读。SEC-26 的能力口径「链路嗅探不可得明文」（被动威胁）已达成；主动 MITM 是无 TLS 体系的固有边界，与 R7（注册链路 staticPubKey 替换窗口）同族、同等知情接受。

**落地注记（v1.72，M5-06 已实施 2026-10-22）**：`Ecies` info 参数化（重载，缺省 `"p2p-ecies"` 既有调用零改动；登录族 `"pcp-login-v1"` 域分离——Core 单测断言双向不可互解）。服务端：ControlSession Hello 处理生成 `EcKeyPair`（Ok/NeedRegister 两路随 HelloAck 下发 Key(8) 65B；版本拒路不带），`UnboxLoginSecret` 开箱、CloseAsync 即 Dispose（用后即焚）；0x20/0x21/0x23 硬切闸=**先于防爆破延迟**（格式闸不构成凭据 oracle），`password_ecies_required` httpLikeMsg；解密失败并入凭据失败口径（0x21 同 login_failed 审计+双维计数；0x23 同 password_change_failed 审计——不泄漏原因）；0x10 死字段 Password 非空同 5004（RegistrationService 顶部）。客户端：ControlClient 握手捕获 loginEphPub + `BoxLoginSecret`（每次现加密——记住我重放非密文重放；缺失抛 `LoginEncryptionUnavailableException` 本地拒绝不回退明文，消息「服务端版本过旧，不支持加密登录，请先升级服务端」，Api.Fail 映射 5004）；三发送点=LoginBindAsync/CreateUserAsync/AuthApi change-password（legacy 字段恒空串）；记住我重放遇旧服务端沿「发送异常保留凭据」语义自动成立（下次重连再试）。测试：Core 消息尾部加法容忍（HelloAck 9→8/0x21 6→5/0x23 7→5 旧线可解）+域分离单测；Server LoginEciesTests 6（明文/缺 Box 5004×2、错钥 0x21/0x23 凭据口径×2、死字段 5004、A-16 帧探针[TestPcpClient SentWire 帧转储+明文对照自证探针敏感]）；Client 本地拒绝单测；集成全量经真客户端栈（明文漏出即被服务端 5004 打断=结构性无明文路径证明）。测试基线全量转 passwordBox（Server.Tests ~50 站点+Integration 3 站点）。

## 11. 登录防爆破（SEC-63，v1.67/M5，M5-04/05）

> 载体双入口：控制信道 0x21/0x23（TCP 7000）与管理端 Web login/change-password（7500）。组件：**LoginThrottle（服务端单例）**——AdminAuthApi 延迟阶梯先例的泛化，三个入口共用（IP 维跨入口共享计数，闭合评估 P1#4「change-password 第二爆破入口」）。

### 11.1 双维计数与递增延迟

| 维 | 键 | 计数来源 |
|---|---|---|
| account 维 | username（精确匹配——库唯一性为 BINARY 折叠，**不做大小写规范化**，防变体绕过） | 0x21/0x23 凭据校验失败 |
| IP 维 | 来源 IP（控制连接 RemoteEndPoint / HTTP RemoteIpAddress） | 0x21/0x23/admin login/admin change-password 四路径失败 |

- 计数：滑动窗 `login_fail_window_sec`（缺省 900s）内失败次数（环形时间戳）；**内存态、重启清零**；键空间上限 8192+空闲清扫（StunGuard 模式）。
- 阶梯：`延迟 = min(500ms × 2^(fails−1), login_delay_cap_ms)`；fails=0 不延迟；**延迟先于凭据校验**（爆破者不可跳过，AdminAuthApi 同款）；延迟期间正确登录同样受当前档延迟（A-15）；账户维**成功即清零**（正常用户的复位语义由账户维兑现）；**IP 维成功不清零**——防同 IP「穿插成功复位」绕过（攻击者间歇以正确账户登录刷新自己 IP 的计数），仅滑窗自然衰减。
- admin 侧：admin 单账户=账户维退化为常量，AdminAuthApi/admin change-password 失败计入 IP 维（与 0x21 共享同组件同 IP 键）——任一入口失败抬高该 IP 全部入口的延迟，第二入口不再独立可绕；AdminAuthApi 既有独立阶梯（[0,500ms,1s,2s,3s] per-IP）**并入统一组件**（封顶随 login_delay_cap_ms=8000，不再各持一套）。

### 11.2 错误语义（M5-01 定案）

**限流触发=延迟后按正常失败应答**（0x21 Ack Ok=false / admin 401{2001}），**不设专用错误码**——专用码向攻击者确认「防护已触发」并指引换维绕过策略（换 IP/换账户探测哪维生效）；延迟应答与凭据错误对外不可区分，零信息泄漏。观测差异仅入审计（`login_throttled`）供管理员侧判断。

### 11.3 审计与解除

- `login_throttled`：**阶跃记录**（每维计数每升一档一条，detail: dim/account 或 ip/fails/delayMs）——逐条记录=爆破风暴下审计自淹（磁盘填充向量），阶跃≤每窗 5 条/键、信息足够；
- 解除可审计=成功事件（既有 `login`/`admin_login`）即复位证据；自动封禁触发见 §13.3。

**落地注记（v1.70，M5-04 已实施 2026-10-22）**：组件=`LoginThrottle`（服务端单例、纯计数不写审计——阶跃审计由各入口携自身 device/user 上下文落，detail=dim/account 或 ip+fails+delayMs；内存态重启清零、键空间 8192+60s 清扫、单键环形时间戳 64 条封顶）；双维键以维名首字符打标互斥；**阶跃判定=延迟值跨档**（达帽后同档不记——封顶 8000ms 即 fails=1~5 各一条）；延迟执行在入口侧用 `Task.Delay(delay, TimeProvider)`（FakeTimeProvider 夹具推进即放行，测试零真实睡眠）。四入口接入：0x21/0x23 经 UserService（可空注入，null=进程内/测试装配跳过；0x23 账户维键=user.Username——与 0x21 同键共享，改密失败同样抬高登录延迟），admin login 经 AdminAuthApi（既有独立 per-IP 阶梯**退役并入**——admin 常量账户维+IP 维双记、成功复位仅账户维、原「成功清 per-IP」语义随 07 §11.1 退场）；admin change-password 入口属 M5-05。参数热更：`login_fail_window_sec`/`login_delay_cap_ms` 入 ConfigDefaults 幂等种子+AdminSystemApi 白名单校验，PUT 后进程内直调 `LoginThrottle.Update` 即时生效（RelayRateLimiter.UpdateRate 同款双写路径，不占 RestartKeys）。

**落地注记（v1.71，M5-05 已实施 2026-10-22）**：admin change-password 入口并入（SEC-63 四入口收口）——延迟先于旧口令校验（同 login：参数 400 校验先于延迟、之后延迟→查行→校验），错旧密码双维计数（admin 常量账户维+IP 维——与 admin login/0x21 同键共享，任一入口失败抬高全部入口延迟），成功仅复位账户维；阶跃审计沿用 `login_throttled`（detail 携 dim/account 或 ip——与改密端点自身 `admin_change_password` 审计各司其职）。

## 12. 监听面资源上限（SEC-64，v1.67/M5，M5-10）

> 目标：防**认证前**资源耗尽（评估 P1#5/N4）。全部 server_config 可配（03 §2.8），缺省=下表定案值。

| 面 | 上限 | 接入点 | 配置键 | 缺省 | 生效 |
|---|---|---|---|---|---|
| 控制端口 | 单 IP 并发连接 | ControlServer accept 后立即 try-acquire（黑名单检查同点，§13.3），超限即关；连接关闭释放 | `control_conn_max_per_ip` | 64 | 运行期现读（即时） |
| 控制端口 | 总并发连接 | 同上（全局计数） | `control_conn_max_total` | 1024 | 运行期现读 |
| 中继 | 单 IP JOIN 到达速率 | UDP：RELAY_JOIN 帧解析前按源 IP 令牌桶（StunGuard 模式，容量=速率）；TCP：首帧 JOIN 前同源 IP 扣桶 | `relay_join_rate_per_ip` | 30（次/s，容量 30） | 运行期现读 |
| 管理 Web | 总连接数 | Kestrel `Limits.MaxConcurrentConnections`（ASP.NET Core 2.0+ 标准 Limiter，缺省 null=不限） | `web_max_connections` | 64 | 启动期设定（restartRequired） |

- 缺省值推演：单 IP 控制连接 64——合法场景=NAT 后整机队（每设备 1 长连接），64 容纳中小办公网队并保留攻击面收敛；总 1024=max_devices 500 的 2 倍余量；JOIN 30/s/IP——正常每设备对每中继会话 2 端 JOIN 各一次，重连风暴下同 IP 聚合亦充裕；Web 64——单管理员+少量标签页（服务端 Web 现无 WS 端点，`MaxConcurrentUpgradedConnections` 不适用，注记防误配）。
- Kestrel 事实核查（learn.microsoft.com，aspnetcore-10.0）：`MaxConcurrentConnections` 自 ASP.NET Core 2.0 起可用、缺省不限；升级连接（WS）不计入本限而由 `MaxConcurrentUpgradedConnections` 独立治理。
- 存量已认证会话不受新上限回溯影响（上限作用于 accept 闸；总连接数收紧时存量会话自然衰减不强制断）。

**落地注记（v1.76/M5-10，SEC-64）**：

- **控制并发闸**：ControlServer `_connGate`（Lock）双计数（per-IP 字典+总量计数），accept 后黑名单检查同点 try-acquire——超限 `client.Close()` 不入会话表（会话表与内存不随连接数无界增长）；两键 accept 时经 ServerConfigStore 现读（控制连接低频——HandleAllocateAsync 每次现读 relay_enabled 同法，PUT 即时生效）；释放在 WatchAsync——**先归还配额再移出会话表**（Sessions 观测到减员即配额已还，测试轮询确定性）。
- **JOIN 速率闸**：新建 Services/RelayJoinGuard（RegistrationGuard/StunGuard TakeNoLock 同款：容量=速率、初始满桶、键空间 8192+60s 空闲清扫；速率单位次/秒），RelayService ctor 以注入 time 构造（假时钟可推进）；rate 值逐次 JOIN 现读传入（容量随调用钳制到新值——热改收紧即时生效、放宽按新速率回填）。UDP 在 JOIN 形状判定后、表查找/认领**前**扣桶；TCP 在首帧 JOIN 校验后**同源同桶**扣桶；数据帧与 KEEPALIVE 不扣（只闸会话建立面）；超限 UDP 静默丢弃/TCP 静默关+`Dropped` 计数（重启清零——观测面，不入审计）。
- **Web 上限**：ServerWebHost.Build `ConfigureKestrel(o => o.Limits.MaxConcurrentConnections = ReadWebMaxConnections(dbFactory))`——启动期单查库行；**行缺省（未初始化库）=null 不设限**（与 Kestrel 缺省同值——ExportTs 裸宿主 EnsureCreated 无行路径不阻断）；`web_max_connections` 入 RestartKeys（管理页重启生效 tag）。
- **存量不回溯**：accept 闸只作用于新连接；收紧后存量会话已持配额自然衰减（WatchAsync 归还）。

### 13.4 踢全部会话（锁定模式定案，M5-09 一键处置）

- 动作=断开**全部**在线 ControlSession（`CloseAsync("security_lockdown")`）+审计 `security_lockdown`；登录态随会话灭（OwnerUserId 会话级，02 §2.5）。
- **不设拒连窗（定案）**：设备凭 deviceSecret 立即可重连（被动同步恢复），主动能力须重新 0x21。已存记住我凭据的设备将自动重放登录（P2 方案 a 语义）——本处置对「持正确密码的设备」无效（它们本就可登录，此为设计语义非缺陷），对「会话内登录态被挪用/异常会话清理/强制全员重认证」有效；**长效封锁用 IP 黑名单**（§13.3），两者互补。
- 备选「踢线+定时拒连窗」被否：误伤自家全部设备（全部被动同步断供）且无增量收益（攻击者若有账号密码照样重登；若没有，登录态作废已达目的）。
- 管理员自身 Web 会话不在处置面（不同监听面与凭据体系）。

**落地注记（v1.75/M5-09）**：`POST /api/security/lockdown`——SecurityApi 经 ServerWebHostService/Build 可空尾参 `control` 持 ControlServer（DI 单例注入；ServerWebHost→ControlServer 单向依赖不引循环），取 `Sessions` 快照逐会话 `CloseAsync("security_lockdown")`+审计 `security_lockdown{kicked:n}`，响应 `{kicked}`；不设拒连窗按定案。管理员 Web 会话不在处置面自然成立（Web 容器连接与 ControlSession 体系隔离，处置面只遍历控制通道会话表）。真会话走查见 §13.2 注记测试条。

## 14. 平台加固（SEC-81~85，v1.67/M5）

### 14.1 服务端最小权限部署（SEC-81，NFR-63，M5-11）

- systemd 单元：专用非特权账户 `User=p2p` / `Group=p2p` + 沙箱指令 `NoNewPrivileges=true`、`ProtectSystem=strict`、`ProtectHome=true`、`PrivateTmp=true`、`ReadWritePaths=/opt/p2p/server/data /opt/p2p/server/logs`、`AmbientCapabilities=CAP_NET_BIND_SERVICE`、`CapabilityBoundingSet=CAP_NET_BIND_SERVICE`。

- Docker 镜像：`USER` 非 root（固定 uid 1000）；3478 绑定依赖容器 cap 集（Docker 默认 cap 含 NET_BIND_SERVICE），环境裁剪 cap 时 `--cap-add=NET_BIND_SERVICE`；`/data` 卷属主 p2p。

### 14.2 客户端本地 Web 请求鉴权（SEC-82，FR-C-813，M5-12）

- **token 生成与轮换**：32B CSPRNG（64 hex），每次服务启动生成，仅内存持有+落 ACL 文件 `web-token`（Windows=`%ProgramData%\P2PClient\web-token`，目录 ACL 既有继承；Linux=`/etc/p2p-client/web-token` 0600）；**服务重启即轮换**（旧 token 立即失效）。
- **载体（定案）**：REST=`Authorization: Bearer <token>`；**WS=`ws://…/ws/status?token=<token>`（query）**——浏览器 WebSocket API 无法自定义请求头，query 是 WS 唯一通用载体；自动打开 URL=`http://127.0.0.1:7100/?token=<token>`（向导 `/wizard?token=…`）——SPA 启动从 URL 读取后存 **sessionStorage**（页面刷新存活、浏览器重启失效，与 token 重启轮换周期匹配），此后 API 调用统一注入 Authorization、WS 连接带 query。
- **校验范围**：全部 `/api/*` 端点与 `/ws/status`；**静态资源豁免**（浏览器 GET 无自定义头能力且 SPA 产物非机密；保护目标是「驱使 SYSTEM 服务执行动作」的 API 面——A-18 后半「裸 HTTP 请求被拒」断言对象即 API）。未携带/错误：REST 401{2001}；WS 升级请求 401 拒绝。
- 威胁收敛评估：收敛「本机任意进程裸 HTTP 驱使 SYSTEM 服务」代理面；不对抗能读 token 文件/进程内存的同机管理员级攻击者（数据目录 ACL/0600 已界定该边界）；监听仍仅 127.0.0.1（D11），不新增远程可达性。
- 兼容：向导首启全流程（自动 URL 进入）不受影响；前端 api.ts 与 WS 客户端统一注入（06 随更注记归 M5-12 实施）。

### 14.3 静态数据加密（SEC-83，M5-13）

- **范围**：`devices.device_secret`（现库唯一凭据类明文列；`users.password_hash` 为单向哈希不入范围）。
- **主密钥来源（定案）**：appsettings `security.masterKey`（64 hex=32B），环境变量 `P2P_MASTER_KEY` 优先覆盖（**密钥不落库**，SEC-83）；**缺失行为=不阻断启动、加密不启用**+启动 ERROR 日志+管理页横幅提示补配——理由：①SEC-83 属 P2 纵深防御层而非运行前提，阻断启动会使存量部署升级即断服；②库文件权限 0600/0750（§14.1）仍是第一道防线；③补配后启动迁移自动完成存量加密（下述）。
- **存储格式**：`[keyTag 1B][nonce 12B][AES-256-GCM(ct‖16B tag)]`，`keyTag = SHA-256(masterKey)[0]`（自动派生，免额外配置项）；device_secret 明文 32B → 密文 61B。EF Core 值转换器透明加解密（读路径零改动）。
- **存量明文库迁移**：启动时 masterKey 在位 → 凡 `device_secret` 长度=32 的行视为明文 → 加密改写（幂等：密文 61B 不再命中判据）；迁移后旧库设备重连不中断（凭据透明可验）。
- **轮换口径**：可选第二钥 `security.masterKeyPrev`（环境变量 `P2P_MASTER_KEY_PREV`）——启动时凡 keyTag≠当前 tag 的密文以 prev 钥解密、以当前钥重加密落库；全部迁移完成后可移除 prev（双钥并存窗口=一次启停）。
- **不可解密文行处置（配错钥，走查回流补定案/OQ-22）**：masterKey 配错且无有效 prev 时，keyTag≠当前 tag 的密文行解密失败——EF 值转换器 **catch 不冒泡**：该行凭据视为失效（等价丢钥：该设备凭据校验失败，恢复路径=管理员解绑后重注册，与下述运维警示同口径）＋ERROR 日志与进程内失败计数（安全中心可见）；启动迁移遇不可解行记 ERROR 跳过、不阻断启动（与「缺钥不阻断」口径对齐）。
- 运维警示（手册承载）：**备份须连同 masterKey**——丢钥后果=旧库凭据不可解，全部设备须管理员解绑后重注册。

### 14.5 控制信道输入长度上限（SEC-85，M5-15）

- 服务端统一 **trim 后 1~64** 校验（与客户端本地 API、0x13 改名同口径，防协议直连绕过）：0x20 `Username`、0x50/0x55 分组名、0x10 `Hostname`。

- 不设配置项（1~64 为协议边界常量）。

**落地注记（v1.80，M5-15 已实施 2026-10-23）**：四处校验统一 `?.Trim() ?? ## 15. 漂移教训与演进纪律（v1.67/M5-01）

### 15.1 §5 漂移实录（教训）

详见 §5.0。要点：设计声称的「频控+max_devices」自 v1.5 起八个版本未实现，直至安全评估正面查实；根因=**列表式防护承诺无任务清单承载、无验收场景锚定**。防再漂移措施：本册 v1.67 起防护类条目逐项标注任务编号（M5-02~15）与验收场景（A-13~A-18），追溯矩阵 10 §10 登记偏差行。

### 15.2 0x10 死字段勘误

02 §2.4 0x10 行「（可选）username+password 同时注册登录（FR-S-101）」为**文档超前于实现**：双端均未使用（客户端恒传 null；服务端 HandleRegisterAsync 不读取该二字段；account 模式实际为 0x10→0x20→0x21 三连）。M5 起服务端对携带 `Password` 的 0x10 一律 5004 拒（§10.3，封堵平行明文通路）；字段保留定义不删（02 §7 禁删改既有字段）。

### 15.3 协议 v2 演进纪律（评估 N9 注记）

协议当前单版本 v1、无算法协商面=已知情现状。**纪律**：未来引入 v2（或任一加密算法替换）时，必须保证双端算法协商**不弱化**——版本协商失败的处理路径（5004/升级引导）不得成为降级到弱算法/明文的通路；「新客户端对旧服务端回退明文」类能力回退一律禁止（本里程碑 OQ-21① 硬切已确立先例）；算法变更必须伴随协议版本递增与服务端「拒绝弱版本」策略，且升级窗口遵循「先客户端、后服务端」单一维护窗口模式。
