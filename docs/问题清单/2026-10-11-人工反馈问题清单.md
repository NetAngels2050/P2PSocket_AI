## 1. P1：登出后再登录报"哑节点模式不允许此操作"（2002）

### 1.1 根因（确定性死锁）

- 能力模式是**连接级状态**：`ControlClient.SetCapability` 只被两处置 Normal——新连接握手完成（ControlClient.cs:371）与注册完成（CompleteRegistration，同连接迁移）；登出走 0x22 后降 Passive 且**连接不断**（FR-C-603 设计：登出不重启会话）。
- 0x21 UserLogin 属**主动类消息清单**（02 §2.5），Passive 会话本地拦截：`ThrowIfPassiveBlocked`（ControlClient.cs:668-683）→ 本地直接抛 `PassiveModeException` → web 层 2002，文案"哑节点模式不允许此操作"（web/ui-shared useApi.ts:14）。
- 登出后心跳正常、连接永不重建 → 主循环 `RunLoopAsync` 不再进入 `ConnectAndHandshakeAsync` → Capability 永远停在 Passive → **同一连接上再发 0x21 必被拒**。
- 设计文档意图（05 §324、02 §2.5）是"重连后再发 0x21"，但**没有任何代码路径触发这次重连**——设计意图未落地，属实现缺陷，可修。

### 1.2 修复 A（已实施）

- `ControlClient`：新增会话代数计数 `_sessionGen`（`ConnectAndHandshakeAsync` 建 Established 时递增）+ 公开 `ReconnectAsync(ct)`：记录当前代数 → 按 `UpdateServerAddrs` 同法杀连接（Cancel backoffWake + dispose _tcp）→ 轮询等待**新代数**的 Established（15s 超时抛 `ControlClientException`）。
- `ClientRegistrationService.LoginBindAsync`：发送 0x21 前若 `client.Capability == Passive` 先 `ReconnectAsync`（新会话初始 Normal，02 §2.5），再发登录——落地文档意图。
- 兼容性：新连接（重启后）初始即 Normal，不触发重连，行为不变；既有手动换址重连路径（设置页/测试⑥）不受影响。

## 2. P2：服务重启后未保持登录态 —— ⏸ 记录跳过，待人工批复

### 2.1 根因（未实现，且为文档化设计语义）

- 客户端从未持久化任何账号凭据：`state.json` 实测无账号字段（deviceId/secretBox/staticPrivateKeyBox/remoteCode/virtualIp/mappings 而已）；`LoginBindAsync`（ClientRegistrationService.cs:125-127）发 0x21 后用户名仅存 web 会话内存 `ctx.LoginUser`，密码不落盘、token 无此机制（0x21 Ack 无凭据下发）。
- 服务端可见性判定用**会话级** `session.OwnerUserId`（仅 0x21 登录设置，GroupService.VisibleDevices）；重启后新会话未登录 → OwnerUserId=null → 0x40 列表只剩共同分组设备。
- 用户手册 v1.0（M4-08）已明示"重新登录才恢复主动能力（设计语义，非故障）"；FR-C-604 只要求控制通道断线重连，不要求登录态续期。
- **修复须改变"凭据不落盘/会话级登录"这一安全设计决策 → 归入"与架构冲突无法自行决定"类，跳过待批复。**

### 2.2 相关口径不一致（缺陷证据，随批复一并裁定）

服务端两处可见性判定口径不一致：`GroupService.VisibleDevices` 用会话级 `session.OwnerUserId`，而 `InvalidationPusher.IsStillVisibleAsync` 用库中 `Device.OwnerUserId`。若批复方案 b（见 §5.1）可顺带对齐。

## 3. P3：登录后映射全部显示"禁用"，须手动停用→启用

### 3.1 根因（恢复链路缺失：启动恢复唯一入口 + 登录无补恢复）

- 启用映射的恢复**唯一入口**是冷启动一次性闸 `RunRegisteredPathAsync`（ClientRuntime.cs:241 `_registeredPathStarted`）内的恢复循环（285-289 行）：逐条 `_sync.EnableAsync`，**失败仅记日志、无任何重试/补发**。
- 启动时序上客户端**必然未登录**（P2：会话级登录）→ `_sync.EnableAsync` 第一步 `ResolvePeerAsync`（MappingSyncService.cs:297-310）走 0x40 按可见性找目标设备 → 无共同分组的目标设备"不存在或不可见" → 抛 4003 → 恢复失败。
- 结果错位：state.json 里 `enabled=true`（配置态），引擎内无运行时 → 列表视图 `List()` 对无快照映射回落 `"disabled"`（MappingSyncService.cs:128-136）→ **web 显示全部禁用**。
- 用户登录成功后，**没有任何代码路径再触发恢复**——这正是用户被迫"停用→启用"（走手动 EnableAsync，此时已登录可见性通过）的原因。属实现缺陷（登录这一可见性前提变化的自然补发动作缺失），可修。

### 3.2 修复 B（已实施）

- `ClientRegistrationService`：新增 `LoginSucceeded` 事件（0x21 Ack.Ok 时触发；向导登录路径同样覆盖）。
- `ClientRuntime`：抽取可重入 `RestoreEnabledMappingsAsync(trigger)`（信号量防并发；逐映射：引擎快照缺失或 Invalid 才补 `_sync.EnableAsync`——不扰 punching/direct/relay/failed 运行态，failed 有自身重试语义；单条失败不连坐）；启动恢复改调它（trigger=startup）；订阅 `LoginSucceeded` 即发即忘补恢复（trigger=login）。
- 引擎侧安全前提（已核）：`MappingEngine.EnableAsync` 对已存在无监听运行时（Failed/Invalid）会先拆旧再重建（MappingEngine.cs:177-184），重复启用安全。
  - **勘误（实机验证后修正）**：上句初版核验有漏——幂等短路在前（177-179 行以 `Listener is not null` 判"在位"），而 MarkInvalid 拆毁运行时**不置空 Listener 字段**，invalid 运行时实际被短路吞掉、先拆后建分支不可达。残留缺陷与修复见 §6.3。

## 4. P4：打洞成功率低（全部中继）

### 4.1 结论：机制有效，非独立代码缺陷

**受控实验（2026-10-11，本机 ↔ 133102，两端 1.0.0+0722853）**：经 API 启用映射 A4-iso-check（tcp，N=3）后 **16s 内打洞成功直连**——local=192.168.1.2:8898、peer=112.31.254.56:9806，服务器 punch_stats 落库 direct/438ms；第二条映射（服务端管理后台 799333→7500）同样 direct；两隧道 viaRelay=false。**证明端口预测法+simultaneous open 在当前两端环境下可用。**

历史数据（服务器 punch_stats，与 M4-06 基准报告一致）：2465 条中 direct 0.53%/relay 99.07%；10-09 当日 0/432 全中继；direct 13 次全部命中 tcp N=3/5。即"平时全中继、实验即直连"并存。

### 4.2 归因

1. **P1~P3 连锁（主因）**：用户观察期映射多处于"禁用错位"状态，手动启停窗口内若 60s 回切循环（M2-19）与打洞超时回退交错，成功直连难出现；修复 A/B 后启用即打洞、登录即恢复，直连机会正常化。
2. **环境因素（叠加，如实记录）**：
   - H2 家宽侧 CGNAT 端口分配漂移：顺序分配是统计倾向非承诺，跨事务漂移则瞄 `+(N−1)` 落空（PRD 02 §3.5 明示随机分配型 NAT 依赖中继回退，非缺陷）；
   - H3 STUN-TCP 探测事务完成后 FIN 优雅关（StunTcpProber finally Close）→ 部分 NAT 立即回收映射，压缩后续 simultaneous open 窗口；
   - H4 运营商 TCP 过滤若非 EIF（endpoint-independent filtering），外部地址连接不回注 listen 口；
   - H5 10s 打洞预算：慢速可穿透组合被超时窗挤压（NFR-14 已如实呈报的固有权衡）。
   - H1 Windows 防火墙：netsh 查证无 p2p-client 入站允许规则——但实验直连成功说明 SYN 经状态化通道可通过，非当前主因；建议项见 §5.2。

### 4.3 修复 C（已实施）：打洞可观测性补强

`Puncher` 构造尾参新增 `log` 缝：TCP 打洞 A/B 两侧建池前输出**计划线**（目标/本端映射端点/端口 L/扇形 N/瞄准端点），池收尾输出**统计线**（LiveConnections/FailedConnects）——后续现场"为何没打成"可从日志直接判 H2/H3/H4/H5 归因，不再依赖猜。宿主 `AttachPuncher` 接 `[punch-tcp]` 前缀日志。

### 4.4 ⏸ 待批复项

- **多偏移扇形扫描**（§5.3）：现单偏移 `+(N−1)` 是 OQ-1 评审决议（TcpPunchPlan.Offsets 注释明言"多偏移扩展点"）；扩为扇形可提升 H2 漂移容错但改决议，须批复。
- **安装器防火墙入站规则**（§5.2）：Setup 加 p2p-client.exe 入站允许规则可消除 H1 变量（有安全面扩大权衡）。

## 5. 待人工批复清单（未修改，仅记录）

### 5.1 P2 登录态保持（二选一或维持现状）

- **方案 a（客户端持凭据）**：DPAPI 加密持久化账号凭据（state.json 增 credentialsBox）+ 启动自动重放 0x21。权衡：SEC-23 威胁模型内"设备持有=账号访问"扩大（物理接触/恶意软件读盘即账号控制）；登出语义需改为"清除凭据"；Windows/Linux（DPAPI/libsecret）双实现。
- **方案 b（服务端会话恢复）**：握手完成后服务端从库 `Device.OwnerUserId` 恢复会话 OwnerUserId（与 InvalidationPusher 口径对齐，顺带修 §2.2 不一致）。权衡：隐式继承设备 owner 的可见性——设备转手/解绑窗口的越权可见风险，须与 02 §2.5 主动/被动能力模型重新对表。
- **维持现状**：接受会话级登录，用户手册口径不变（P3 修复后重启仅需一次登录即全量恢复，体验损失已收窄）。

### 5.2 安装器防火墙入站规则

Setup 增加 p2p-client.exe 入站允许规则（或文档指导用户加）。权衡：收窄 H1 不确定性 vs 放开本机任意入站到客户端进程的攻击面。

### 5.3 TCP 打洞多偏移扇形

`TcpPunchPlan.Offsets(N)` 由 `[N−1]` 扩为多偏移扇形（如 0/±1 按权重分配 connect 数），改 OQ-1 单偏移决议。收益：H2 端口漂移容错；代价：扇形摊薄每目标 connect 重试密度、NAT 状态表占用上升。

### 5.4 诊断盲区注记（无需批复，记录备忘）

服务器单公网 IP 未配 stun_alt_addr → stun-test 的 tcpPortDependent 判型不可判（降级）。如需该判型，服务器须配第二公网 IP；否则维持现状并在排障指南注明局限。
