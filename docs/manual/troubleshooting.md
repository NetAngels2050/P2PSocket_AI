# P2P 排障指南

> 适用版本：1.0.0　依据：NFR-62、设计 08 §8、M1~M3 实机踩坑实录　随版交付（M4-09）
> 用法：按「§0 症状速查表」定位条目号 → 跳转详细条目（症状/常见原因/处置步骤/验证方法/日志关键词）。日志文案与错误码均对照源码 grep 核对。操作类背景见[用户使用手册](用户使用手册.md)；安装升级类见[部署手册](../deploy/)。

## 0. 日志与状态在哪里看

| 位置 | 路径/入口 |
|---|---|
| 客户端 Web 日志页 | `http://127.0.0.1:7100/logs`（级别过滤+导出，newest-first） |
| 客户端日志文件（Windows） | `C:\ProgramData\P2PClient\logs\client-<日期>.log` |
| 客户端日志文件（Linux） | `/etc/p2p-client/logs/client-<日期>.log`（deb 布局；手工部署在部署目录 logs/ 下） |
| 服务端日志 | 部署目录 `logs/app-<日期>.log`（滚动 10MB）+ `journalctl -u p2p-server -f` |
| 映射状态/失败明细 | 客户端「端口映射」页状态列与失败明细（`打洞失败 peer=…：<原因>`） |
| 服务端打洞统计 | 管理后台「仪表盘」打洞成功率/「系统」审计日志（事件过滤） |

日志前缀读法：`[control]`=控制通道、`[punch]`=打洞、`[relay]`=中继、`[engine]`=映射引擎、`[nic]`=虚拟网卡、`[restore]`=启动恢复、`[report]`=状态上报。

## §1 打洞超时（punch_timeout，NAT 组合不可穿透）

**症状**：映射启用后长时间「打洞中」，终态「失败」，失败明细含 `punch_timeout`；两端设备都在线、服务端可达。

**常见原因**：双方 NAT 组合不可穿透——典型为**一端 Symmetric（运营商 CGNAT 常见）×另一端锥形**，UDP 端口预测失配、TCP 预测无规律可循（实机实录：家宽 CGNAT 10.x 内网出口漂移 × PortRestrictedCone，四环节排查全正常但双侧打洞包零到达）。

**处置步骤**：
1. 双方各自在「设置 → 网络诊断（NAT 判型）」跑判型（受限型 NAT 须等超时判据，**全程可数十秒**）；
2. 对照判型：任一方「UDP 映射类型=地址端口相关映射（symmetric）」→ UDP 直连基本无望；看「TCP 端口分配」——**同时打开**（N=1 即可）仍有机会，**随机**则直连无解；
3. 无解组合走中继：**目标设备**开「中继回退」开关（设备页）→ 映射「重试」→ 转「中继」态正常使用；
4. 若对端在家宽且你可控网络环境，换网络（如手机热点）有时恰好换到锥形 NAT——重跑判型确认。

**验证方法**：映射状态变「中继」且应用可访问；服务端「中继」页出现该会话，转发字节随使用增长。

**日志关键词**：`打洞失败 peer=`、`punch_timeout`、`[punch]`。

## §2 云服务器上的客户端打洞必超时（安全组挡随机打洞端口）

**症状**：公网 VPS 上装的客户端，与任何设备打洞都 punch_timeout（实机实录：服务器侧客户端）。

**常见原因**：打洞端口是双方临时协商的**随机高位端口**，云安全组只放行了固定端口（7000/3478/7010-7020）——打洞包到达就被丢。这是**部署拓扑的必然结果，不是产品缺陷**。

**处置步骤**：
1. 确认设备页已给该云服务器设备**开启「中继回退」**——该形态下中继是常态承载；
2. （可选但开销大）在安全组放行一大段高位 UDP/TCP 端口可提高直连率，一般不值得；
3. 对端（家庭/办公设备）侧无需任何改动。

**验证方法**：映射转「中继」态；服务端仪表盘 punch_stats 里该对端 relay 占比高属预期。

**日志关键词**：`punch_timeout`、`[punch]`；服务端侧可用 `tcpdump` 观察打洞端口零到达（参照服务端部署手册 §stun 验证姿势）。

## §3 打洞失败后没有转中继（failed 而非「中继」）

**症状**：打洞失败，映射终态「失败」而不是「中继」，无 relay_failed 字样。

**常见原因**：**目标设备的中继回退开关未开启**（回退是设备级开关，D3 决策——目标设备层级；本机开关不影响别人打到本机）。

**处置步骤**：
1. 在**目标设备**的「设备发现」页（或其本机管理页）确认该设备行「中继回退」开关已开启（peers 配置即时生效，无需重启）；
2. 回到发起端映射页点「重试」。

**验证方法**：重试后先短暂「打洞中」再转「中继」。

**日志关键词**：`打洞失败 peer=`（FailReason=punch_timeout 无 `relay_failed` 后缀=无回退资格）；开关开启后失败明细出现 `；relay_failed: …` 才是回退也失败。

## §4 4002 段外目标（L3 白名单）

**症状**：新建/编辑映射（IP 模式）被拒，错误码 4002。

**常见原因**：目标地址不在**目标设备**配置的开放网段白名单内（L3 授权 fail closed——留空=全拒，self 模式不受限）。

**处置步骤**：
1. 看映射表单下方的「对端开放网段」提示（已列出对端网段），确认目标地址落在某网段内；
2. 不在则联系对端在其「网段」页添加对应 CIDR（即时生效；全开放须**显式** `0.0.0.0/0`）；
3. 改回表单重新保存。注意：对端**删网段**会使引用该段的既有映射立即「失效」（§8）。

**验证方法**：保存成功；对端日志无 `l3_not_permitted`。

**日志关键词**：客户端 `l3_not_permitted: <地址>`（引擎侧拦截）；4002（服务端侧拦截，两端各一道闸）。

## §5 4003 远程码失效（对端重置过码）

**症状**：新建/编辑映射报 4003；或对端设备的既有映射突然「失效」并弹出全局失效提示。

**常见原因**：目标设备**重置过远程码**——旧码立即失效（0x75 推送失效，引用旧码的映射被打.Invalid）。

**处置步骤**：
1. 向对端确认新远程码（重置成功弹窗只展示一次）；
2. 编辑失效映射把目标远程码改为新码 → 重新启用。

**验证方法**：映射恢复直达/中继；设备页远程码列与新码一致。

**日志关键词**：`[control] 0x75 失效推送（reason=remote_code_reset`。

## §6 4003 从未重置过码（可见性丢失——老设备常见）

**症状**：远程码明明正确却报 4003（实机实录：M1 时期注册的老设备）。

**常见原因**：**双方互相不可见**——可见性=同账号 ∪ 同分组。早期版本注册的设备可能既无账号绑定也不在默认分组（注册即入默认分组是后来行为），与其它设备零可见性通道；退组/被移出/分组解散同理。

**处置步骤**：
1. 检查双方是否登录**同一账号**（账号页看登录态），或处于**同一分组**（设备页看分组列）；
2. 都不是 → 补建立：两端登录同一账号，或一端把另一端凭码/邀请码拉进同组；
3. 重试映射操作。

**验证方法**：设备页「设备发现」能互相看到对方（列表本身就按可见性过滤）。

**日志关键词**：4003（REMOTE_CODE_INVALID——含不可见与离线两类解析失败）；服务端审计 `passive_deny`/分组事件可佐证成员关系。

## §7 4005 目标设备离线

**症状**：打洞请求被拒，错误码 4005。

**常见原因**：目标设备当前不在线（断网/服务停了/被禁用踢线）。

**处置步骤**：
1. 设备页看对端**在线状态**（列表为事件驱动，对端上下线自动刷新）；
2. 离线 → 对端恢复后重试；被禁用 → 联系管理员启用（§20 服务端设备页）。

**验证方法**：设备页对端显示在线后再「重试」。

**日志关键词**：`server_4005: target_offline`（打洞失败明细内）。

## §8 映射曾通，现在「失效」或「失败」（授权/环境变更）

**症状**：之前正常的映射变灰「失效」，或运行中断开后转「失败」。

**常见原因**（按 0x75 失效推送的 reason 区分）：
- `lan_segment_removed`：对端删除了覆盖目标地址的网段（段外访问被收回）；
- `remote_code_reset`：本机或对端重置了远程码（§5）；
- `device_disabled` / `user_disabled`：设备被禁用踢线/用户被禁用降级；
- `group_left` / `group_dissolved` / 成员移出：可见性边被切断（§6）；
- 「失败」且明细 `punch_timeout`：网络环境变化导致原 NAT 组合不再可穿透（§1）。

**处置步骤**：
1. 失效映射上看失败明细/全局提示的 reason；或日志搜 `[control] 0x75 失效推送（reason=`；
2. 按 reason 对应处置：补网段（§4）/换新码（§5）/恢复分组或登录（§6）/等管理员启用；
3. 编辑修正后重新启用。

**验证方法**：映射状态回到直达/中继且应用可访问。

**日志关键词**：`[control] 0x75 失效推送（reason=`、`[engine] 0x75 映射 … 失效处理`。

## §9 listen_failed（端口占用 / 重启后短暂失败）

**症状**：映射「失败」，明细 `listen_failed: AddressAlreadyInUse`（真占用）或 `listen_failed: AddressNotAvailable`（重启竞态）。

**常见原因**：
- **AddressAlreadyInUse**：本机虚拟 IP 100.64.0.2 上该端口已被其它映射/程序占用（注意：虚拟 IP 与 127.0.0.1 是**两个独立监听位**——127.0.0.1 上有同名端口不冲突，100.64.0.2 上有才冲突）；
- **AddressNotAvailable**：服务重启瞬间的 Wintun 适配器切换窗口（IP 未对 TCP 栈生效）——**已知且已自愈**：引擎每 5s 自动重试+网卡恢复沿立即触发，无需人工。

**处置步骤**：
1. `AddressNotAvailable` → 不用管，观察状态自动恢复（日志可见 `映射 … 监听自动重试（listen_failed 自愈，M2-24）`）；
2. `AddressAlreadyInUse` → 管理员命令查占用：Windows `netstat -ano | findstr :端口`（注意看绑定列是否 100.64.0.2）；Linux `ss -tlnp | grep :端口`；改用其它本地端口或停掉占用程序。

**验证方法**：映射状态离开「失败」。

**日志关键词**：`listen_failed: AddressAlreadyInUse`、`listen_failed: AddressNotAvailable`、`监听自动重试（listen_failed 自愈`。

## §10 本机应用连不上映射端口（虚拟 IP 绑定语义）

**症状**：映射状态直达/中继正常，但本机应用 `connection refused`。

**常见原因**：
1. **连错地址**——映射监听绑在虚拟 IP **100.64.0.2** 上，不是 127.0.0.1（实机实录：`http://127.0.0.1:8080` 不通而 `http://100.64.0.2:8080` 通）；
2. 本机物理网络与虚拟网段 100.64.0.0/24 重叠（顶部会持续显示「虚拟网段冲突」告警条）；
3. 映射实际处于失败/失效/停用态（看状态列）。

**处置步骤**：
1. 应用改连 `100.64.0.2:<本地端口>`；
2. 有网段冲突告警 → 调整本机网络避开 100.64.0.0/24，或管理员改服务端 `virtual_subnet` 键（重启生效）；
3. 状态不对 → 先按对应条目恢复。

**验证方法**：`ping 100.64.0.2` 通 + 应用连接成功；`netstat`/`ss` 可见 100.64.0.2:端口 LISTEN。

**日志关键词**：客户端「设置 → 设备连通性」隧道 PING 直接验证（§6.2 使用手册）；冲突条= `subnet_conflict`。

## §11 Windows：Wintun 加载失败

**症状**：客户端启动/注册报「未找到 Wintun.dll」或驱动相关 Win32 错误；注册不完成、虚拟网卡不出现。

**常见原因**：程序目录缺 `Wintun.dll`（portable 手工部署漏拷；官方包 wintun.net 取 `bin/amd64/wintun.dll`）；或服务未以管理员/LocalSystem 运行（驱动加载需权限）。

**处置步骤**：
1. 补 `Wintun.dll` 到**程序目录**（与 exe 同目录）→ 重启 P2PClient 服务；
2. 确认服务运行账户=LocalSystem（安装脚本/Setup 默认即是）；手工跑 exe 须管理员；
3. 仍失败看日志 Win32 错误码（WintunStartSession 等）。

**验证方法**：注册后 `ipconfig` 出现虚拟网卡且 IPv4=100.64.0.2。

**日志关键词**：`未找到 Wintun.dll：请随安装包置于程序目录`、`[nic]`。

## §12 Linux：TUN 设备/权限错误

**症状**：注册或网卡应用报错：无法打开 /dev/net/tun / rtnetlink errno / SIOCGIFINDEX 相关。

**常见原因**：
1. 容器/精简内核无 TUN 设备（`/dev/net/tun` 不存在——容器须显式挂载）；
2. 未加载 tun 模块；
3. 以非 root/无 CAP_NET_ADMIN 运行（systemd 单元默认 root 无此问题；手工前台跑易踩）。

**处置步骤**：
1. `ls /dev/net/tun`——不存在则宿主 `modprobe tun`（容器：docker run 加 `--device /dev/net/tun`）；
2. 确认服务 root 运行（`ps -o user= -p $(pidof p2p-client)`）；
3. `iproute2` 依赖缺失时 `apt install iproute2`（deb 包已声明依赖）。

**验证方法**：注册后 `ip link` 出现 `p2p-tun` 且 inet 100.64.0.2。

**日志关键词**：`无法打开 /dev/net/tun：内核需加载 tun 模块（modprobe tun）`、`拉起接口 p2p-tun 失败：rtnetlink errno`。

## §13 服务端不可达（向导测试失败/客户端反复重连）

**症状**：向导「测试连接」失败；或已注册客户端日志刷 `连接 … 失败` / `退避 Ns 后重连`。

**常见原因**：
1. 地址或端口写错（应为 `<IP>:7000`）；
2. 服务端安全组/防火墙未放行 **7000/TCP**；
3. 服务端进程未运行；
4. 服务端版本太旧协议不符（那会走升级页 §17，不会一直重连）。

**处置步骤**：
1. 服务端机器 `systemctl status p2p-server`（应 active；首启 ~12s 内 activating 属正常）；
2. 探测端口：`tcping <IP> 7000` 或 `bash -c 'echo > /dev/tcp/<IP>/7000'`；
3. 安全组核对放行清单（7000/TCP、3478 TCP+UDP、7010-7020 TCP+UDP 必须；见服务端部署手册端口表）；
4. 客户端「设置 → 服务端连通性」多候选逐个探测定位坏线路；改服务端地址候选（设置页）后自动重连。

**验证方法**：向导测试「连接成功」；日志 `[control]` 不再刷退避。

**日志关键词**：`连接 {host}:{port} 失败`、`退避 …s 后重连`、`[control]`。

## §14 服务端管理后台 7500 打不开

**症状**：浏览器访问 `http://<服务端>:7500` 超时/拒绝。

**常见原因**：**设计使然**——管理面默认仅绑定 127.0.0.1（不对公网暴露，D11 安全不变式），且安全组不放行 7500。不是故障。

**处置步骤**（两选一）：
1. **SSH 隧道（兜底）**：`ssh -L 7500:127.0.0.1:7500 <服务端>` 后本机访问 `http://127.0.0.1:7500`；
2. **经客户端映射（正式路径）**：在服务端机上装客户端并注册（该形态打洞必被安全组挡→**开中继回退**，§2），在管理员电脑建映射 `本地端口 → 该设备远程码 / self:7500`，访问 `http://100.64.0.2:<本地端口>`（实机实录即此形态）。

**验证方法**：隧道/映射路径下能出登录页（admin/admin 首登强制改密）。

**日志关键词**：不适用（网络层不可达）；核实绑定 `ss -tlnp | grep 7500` 应只见 127.0.0.1。

## §15 中继转发慢

**症状**：中继态映射速率明显低于直连/预期。

**常见原因**：
1. **部署拓扑常态**：中继走服务端带宽，受服务端出口带宽与两段 RTT 约束（云 VPS 小水管是硬上限）；
2. 服务端配置了 `relay_rate_limit` 限速（全局令牌桶——存量降速等待，不打断）；
3. 多设备共享同一中继带宽。

**处置步骤**：
1. 管理后台「中继」页看限速配置与活跃会话数（多会话均分限速值）；
2. 需要提速：调高/清零 `relay_rate_limit`（0=不限，即时生效）或升级服务端带宽；
3. 追求速率：按 §1 评估直连可能性（开中继回退不影响继续尝试直连——回切机制每 60s 重试）。

**验证方法**：中继页会话「转发字节」增速与限速值量级一致；限速改动后新流量立即变化。

**日志关键词**：`[relay]`；服务端审计 `relay_config_change`。

## §16 中继分配被拒（5002）

**症状**：打洞失败后回退也失败，明细含 `relay_failed` 或 `5002`。

**常见原因**：服务端**中继服务关闭**（`relay_enabled=0`——关闭=拒新分配，存量会话不受影响继续转发）或**限速耗尽**（`relay_rate_limited`——桶空时新分配被拒）。

**处置步骤**：
1. 管理后台「中继」页：看服务开关与限速值；
2. 打开服务（确认弹窗已说明语义：恢复新分配放行）/调高限速；
3. 客户端映射「重试」。

**验证方法**：重试后转「中继」；服务端日志/审计无新 5002。

**日志关键词**：`server_5002: relay_disabled`、`server_5002: relay_rate_limited`、`relay_failed`。

## §17 协议版本不符（自动弹升级页）

**症状**：客户端连不上且浏览器自动打开 `/upgrade?reason=version` 顶部「协议版本不兼容」警示。

**常见原因**：客户端协议版本在服务端兼容范围外（服务端升级后旧客户端常见；反向上限=宿主编译版本）。

**处置步骤**：
1. 升级页按「下载地址」取新版本（内容由服务端 `update_*` 四键配置）；
2. 按部署手册升级（Windows 重跑 Setup/portable 停覆盖起；覆盖安装**不丢数据**——配置/凭据/映射在数据目录）；
3. 升级后自动重连，无需重新注册。

**验证方法**：重连成功（顶栏不再「本地服务不可达」）；「设置 → 关于」版本与下载版本一致。

**日志关键词**：`[control] 升级引导：服务端要求 <版本>`、5004。

## §18 客户端管理页 7100 打不开

**症状**：浏览器访问 `http://127.0.0.1:7100` 失败或顶栏「本地服务不可达」。

**常见原因**：服务未运行；Linux/远程机上 7100 仅回环、你在别的机器访问。

**处置步骤**：
1. Windows `Get-Service P2PClient` / Linux `systemctl status p2p-client`——未运行则启动（注意 deb 首装**有意不自动启动**，须向导注册后手工 `systemctl start`）；
2. 远程机：`ssh -L 7100:127.0.0.1:7100 <主机>` 后本机访问；
3. 本地 Web 端口被改过（设置页改端口重启生效——用新端口访问）。

**验证方法**：`curl -I http://127.0.0.1:7100/wizard` 返回 200。

**日志关键词**：不适用（Web 层不可达先看进程）；服务日志 `未注册：向导模式已就绪` = 进程活着等注册。

## §19 主动操作被拒 2002（哑节点）

**症状**：映射/分组等页按钮全灰，页面顶部「哑节点」横幅；直接登录报「登录须重建控制通道」提示。

**常见原因**：本机处于哑节点（登出过/用户被禁用降级）——主动类操作（启停映射、分组管理、改密）全部被拒（2002），仅响应既有隧道。

**处置步骤**：
1. 普通登出 → 「账号」页重新登录即可恢复；
2. 提示须重连 → 等待自动重连（日志退避周期）或重启客户端服务后再登录；
3. 用户被禁用 → 联系管理员启用后**重连+重新登录**（设计语义：enable 不自动恢复会话能力）。

**验证方法**：顶栏显示 `用户名（已登录）`；按钮恢复可用。

**日志关键词**：2002/FORBIDDEN_PASSIVE、服务端审计 `passive_deny`。

## §20 服务端升级后起不来

**症状**：升级二进制后 `systemctl status p2p-server` 反复重启/失败。

**常见原因**：
1. 新版配置键缺失/损坏（理论上 DbInitializer 自动补键——除非数据库文件权限/路径变了）；
2. appsettings.json 被覆盖丢失线上改动（如 webBind/database.path 自定义值）；
3. 数据库被降级打开（EF schema 只进不退——旧二进制+新库不支持）。

**处置步骤**：
1. `journalctl -u p2p-server -n 50` 看首个异常——两类启动期拒绝均有明文：
   - `数据库初始化失败，拒绝启动（NFR-35）：…` → 检查 data 目录/`p2p.db` 文件权限与路径（appsettings `database.path` 是否被覆盖改动）；
   - `配置校验失败，拒绝启动（NFR-35）：…`（逐行列出问题，如缺 appsettings.json）→ 从发布包恢复/比对升级前备份补回自定义键；
2. 与升级前备份的 appsettings.json 比对补回线上改动（webBind/database.path 等自定义值）；
3. 仍失败 → 用升级前的二进制备份回滚（bak 文件覆盖回去 restart，见服务端部署手册 §升级与回滚）。

**验证方法**：`systemctl is-active p2p-server` = active；`curl 127.0.0.1:7500` 登录页可达。

**日志关键词**：`数据库初始化失败，拒绝启动`、`配置校验失败，拒绝启动`。
